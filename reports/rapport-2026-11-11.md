### 2. GitHub va suspendre les alertes Dependabot sur les dépôts inactifs depuis un an

À partir du 8 décembre 2026, GitHub désactive les alertes Dependabot sur la plupart des dépôts sans activité depuis un an (aucun push, création ou activation des alertes). Les alertes existantes sont archivées, pas supprimées. Un push ou une réactivation dans les paramètres les restaure et relance le compteur d'un an. Les dépôts couverts par une configuration de sécurité imposée sont exemptés. Le changement concerne github.com et GitHub Enterprise Cloud avec résidence des données, pas GitHub Enterprise Server.

- **Date de publication :** 10 novembre 2026
- **Source :** [GitHub Changelog](https://github.blog/changelog/2026-11-10-dependabot-alerts-will-pause-on-inactive-repositories/)
- **Pourquoi c'est important pour un développeur :** Un vieux dépôt toujours déployé (petite API, site vitrine, package interne) ne te préviendra plus des dépendances vulnérables. Fais l'inventaire de ces dépôts avant le 8 décembre et impose les alertes via une configuration de sécurité pour ceux qui tournent encore en production.

### 🛠️ Technique et bonne pratique

**Déléguer les tâches bruyantes à un sous-agent.** Un sous-agent Claude Code tourne dans sa propre fenêtre de contexte, avec son propre prompt système, ses outils et ses permissions. Les sorties volumineuses (logs de tests, résultats de recherche, contenu de fichiers) restent chez lui : seul son résumé revient dans la conversation principale. La documentation conseille d'y recourir quand une tâche annexe noierait le contexte principal, ou quand tu lances souvent le même type de travail. Limite ses outils au strict nécessaire (lecture seule pour la revue et la recherche), et confie les tâches simples à `haiku` pour réduire les coûts. Garde la conversation principale pour ce qui demande des allers-retours ou une faible latence.

### 🔌 Outils et intégrations

Un sous-agent est un fichier Markdown avec un en-tête YAML : `.claude/agents/` pour le projet (à versionner pour l'équipe), `~/.claude/agents/` pour tous tes projets. Seuls `name` et `description` sont obligatoires ; les champs utiles sont `tools` (liste autorisée), `disallowedTools` (liste interdite), `model` (`sonnet`, `opus`, `haiku`, `fable` ou `inherit`), `permissionMode`, `maxTurns` et `memory: project`. Attention : les noms de champs sont en camelCase et un champ mal orthographié est ignoré sans message. Claude choisit le sous-agent d'après sa `description` : ajoute « use proactively » pour encourager la délégation automatique. Pour l'appeler explicitement : `@"code-reviewer (agent)"` ou `claude --agent code-reviewer` pour toute une session.

### 💡 Exemple d'utilisation

Crée `.claude/agents/test-runner.md` dans ton projet Spring Boot :

```markdown
---
name: test-runner
description: Lance les tests Maven et résume uniquement les échecs. Use proactively après une modification de code Java.
tools: Bash, Read, Grep
model: haiku
---

Lance `./mvnw -q test`. Si des tests échouent, lis les rapports dans
target/surefire-reports et renvoie pour chaque échec : classe, méthode,
message d'erreur et ligne en cause. Ne modifie aucun fichier.
```

Ensuite, demande « corrige le bug de calcul de TVA dans OrderService » : Claude délègue l'exécution des tests au sous-agent, qui avale les centaines de lignes de logs Maven et ne renvoie que la liste des échecs. Le contexte principal reste propre pour la correction.

## G. Le défi technique du jour : Trouver les dépôts « endormis » avant la coupure des alertes Dependabot

**Niveau :** Débutant à intermédiaire · **Durée :** 40 min · **Technologies :** SQL (PostgreSQL)

Inspiré du changement de GitHub sur Dependabot. Crée trois tables : `repos(id, nom, en_production boolean, cree_le timestamp)`, `pushes(id, repo_id, pousse_le timestamp)` et `alertes(id, repo_id, severite text, ouverte boolean)`. Insère une dizaine de dépôts avec des historiques variés. Écris ensuite une requête qui renvoie, pour chaque dépôt, la date de dernière activité (dernier push ou date de création si aucun push), le nombre de jours d'inactivité et un statut : « sera mis en pause » si plus de 365 jours sans activité, sinon « actif ». Trie en mettant en tête les dépôts en production qui seront mis en pause et qui ont des alertes ouvertes de sévérité « critical » ou « high ».

**Indices :**

- Utilise `COALESCE(MAX(p.pousse_le), r.cree_le)` avec un `LEFT JOIN` pour gérer les dépôts sans aucun push.
- Calcule l'inactivité avec `now() - derniere_activite > interval '365 days'` dans une expression `CASE`.
- Compte les alertes graves avec `COUNT(*) FILTER (WHERE a.ouverte AND a.severite IN ('critical','high'))` dans une sous-requête ou une CTE séparée, pour éviter de multiplier les lignes par la jointure sur les pushes.

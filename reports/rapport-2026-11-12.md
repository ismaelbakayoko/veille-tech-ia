### 2. Apache HTTP Server : faille critique d'exécution de code à distance dans mod_http2 (CVE-2026-119618)

Une condition de course dans mod_http2 permet à un attaquant distant non authentifié de corrompre la mémoire du tas et potentiellement d'exécuter du code avec les droits du serveur web. Versions touchées : 2.4.55 à 2.4.70 avec HTTP/2 activé, et le module mod_h2 autonome 2.0.8 à 2.0.42. Correctif : Apache 2.4.71. Selon Wiz, aucun exploit public ni exploitation connue au moment de la publication.

- **Date de publication :** 11 novembre 2026
- **Source :** [Wiz](https://www.wiz.io/blog/cve-2026-119618-rce-apache-http-server-vulnerability)
- **Pourquoi c'est important pour un développeur :** Vérifie `httpd -v` sur tes serveurs et reverse proxies (devant une app Spring Boot ou PHP par exemple). Si tu ne peux pas passer en 2.4.71 tout de suite, désactive HTTP/2 avec `Protocols http/1.1` en attendant.

### 3. AWS lance AWS Emulator, un émulateur local officiel et open source des services AWS

AWS Emulator, écrit en Rust, reçoit les appels du CLI et des SDK AWS sur un endpoint HTTPS local (127.0.0.1:9297 par défaut), sans compte AWS. Les services sont générés depuis les modèles d'API publiés par AWS ; une opération non prise en charge renvoie HTTP 501 et un rapport de fidélité compare les réponses à celles d'AWS. L'état reste en mémoire, chaque instance est isolée (pratique pour des tests en parallèle). Limites au lancement : pas d'évaluation des politiques IAM, un seul compte, pas de comportement inter-régions. Gratuit, code sous CC0 ; AWS indique qu'il est construit et maintenu par des agents.

- **Date de publication :** 11 novembre 2026
- **Source :** [AWS News Blog](https://aws.amazon.com/blogs/aws/test-your-applications-against-aws-locally-with-aws-emulator/)
- **Pourquoi c'est important pour un développeur :** Tes tests d'intégration S3, SQS ou DynamoDB peuvent tourner en local et en CI sans facture ni credentials réels. Attention : comme IAM n'est pas évalué, un test qui passe en local ne prouve rien sur tes permissions.

### 🛠️ Technique et bonne pratique

**Lancer Claude Code sans surveillance, en toute sécurité.** En CI ou dans une tâche planifiée, personne ne peut répondre aux demandes de permission. La documentation propose trois réglages. 1) `--bare` : Claude Code ne charge ni les hooks, ni les plugins, ni les serveurs MCP, ni le CLAUDE.md de la machine, donc le résultat est le même partout (il faut alors fournir `ANTHROPIC_API_KEY`). 2) `--permission-mode dontAsk` : tout appel qui demanderait une permission est refusé ; seuls passent les lectures dans le dossier de travail, les commandes en lecture seule et ce que tu autorises avec `--allowedTools`. 3) `--permission-prompts none` (v2.1.259+) : Claude est prévenu que personne ne peut approuver et ne réessaie pas en boucle.

### 🔌 Outils et intégrations

Pour exploiter le résultat dans un script : `--output-format json` renvoie un objet avec `result`, `session_id` et `total_cost_usd` ; avec `--json-schema`, la réponse structurée arrive dans le champ `structured_output` (vérifie qu'il existe avant de l'utiliser : il est absent si Claude a refusé). Claude Code sort avec le code 0 en cas de succès et un code non nul en cas d'échec, ce qui permet de faire échouer un job CI. En `stream-json`, les refus apparaissent comme messages `permission_denied`.

### 💡 Exemple d'utilisation

Revue de sécurité automatique d'une pull request dans GitHub Actions : `gh pr diff "$PR" | claude --bare -p --append-system-prompt "Tu es un ingénieur sécurité. Signale les failles." --permission-mode dontAsk --output-format json | jq -r '.result' > revue.md`. Le diff arrive par stdin, donc Claude n'a besoin d'aucune permission Bash pour le lire ; le mode `dontAsk` garantit qu'il ne modifiera rien.

## G. Le défi technique du jour : Tester un service d'upload S3 Spring Boot contre AWS Emulator

**Niveau :** Intermédiaire · **Durée :** 45-60 min · **Technologies :** Java 21, Spring Boot, AWS SDK for Java v2, JUnit 5

Inspiré du lancement d'AWS Emulator. Crée un service Spring Boot `DocumentService` avec trois méthodes : `upload(String nom, byte[] contenu)` qui envoie un fichier dans un bucket S3, `telecharger(String nom)` qui renvoie son contenu, et `lister()` qui renvoie la liste des noms de fichiers. L'URL de l'endpoint S3 doit venir de la configuration (`app.s3.endpoint`), pas du code. Écris ensuite trois tests d'intégration qui tournent contre AWS Emulator lancé en local : un upload suivi d'un listing, un upload de deux fichiers portant le même nom (le second écrase le premier), et la lecture d'un fichier inexistant (vérifie l'exception levée). Les tests ne doivent utiliser aucune credential AWS réelle.

**Indices :**

- Avec le SDK v2, `S3Client.builder().endpointOverride(URI.create(endpoint))` redirige les appels vers l'émulateur ; pense aussi à `forcePathStyle(true)`.
- Crée le bucket dans une méthode `@BeforeEach` et utilise un nom unique par test pour isoler les cas.
- Garde en tête qu'IAM n'est pas évalué par l'émulateur : ne teste pas les refus d'accès ici.
